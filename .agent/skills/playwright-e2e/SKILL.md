# DMS Playwright End-to-End Testing

Implement browser tests under `src/client/e2e` and follow
`.github/instructions/playwright.instructions.md`.

Keep and preserve Angular unit and component specs colocated with their source
under `src/client/src/app` for Jasmine/Karma. Never move or delete `TestBed`,
Jasmine spies, or collaborator-level unit assertions when adding complementary
coverage in `src/client/e2e`.

## Workflow

1. Translate the requirement into a short list of observable outcomes. Identify the user role and authorization flags, starting state, seeded records or explicit no-seed contract, allowed mutations, and cleanup expectations. Admin Settings journeys require the dedicated E2E user to be a system administrator.
2. Inspect the owning route and rendered UI. Use the Playwright MCP server for accessibility-tree exploration when the local app is running; treat exploration as discovery, not as the committed regression test.
3. Before adding or running a data-dependent scenario, ask clarification questions when identity, seeded or reference data, approved browser/API mutations, state-specific fixtures, or cleanup behavior is missing. Never invent credentials, record names, reference data, mutation scope, or cleanup behavior; read-only scenarios may proceed without mutation approval, while mutations require explicit approval and a deterministic contract.
4. Before execution, explain that global setup renews the dedicated E2E user's `LoginInfo` and wait for explicit human approval. Also identify any additional create, update, or delete operations in the journey.
5. Add or update the smallest independent `*.spec.ts` test. Prefer roles and labels, and assert the business-visible result rather than framework state.
6. After approval, run `npm run test:e2e -- <relative-spec-path>` from `src/client`. The custom runner preserves Node TLS validation for the local Aspire certificate, prevents overlapping executions, and global setup creates temporary ignored storage state through the signed E2E session endpoint.
7. Classify each supported failure as product, test, test data, or environment. Fix only test defects unless the user authorizes application changes.
8. Rerun the focused spec after each repair. From the repository root, run `./start.sh e2e` before completion when the required local services and seeded data are available. The wrapper ensures Chromium is installed and executes the complete suite.
9. Report scenarios added or changed, commands run, pass/fail counts, artifact locations, mutations performed, and remaining coverage gaps.

## Seed Data Source Of Truth

- Treat `src/client/e2e/fixtures/<model>.seed.json` and its typed `<model>.seed.ts` wrapper as the single source of truth for all data used by a test journey.
- Put every related model needed by the journey in that fixture, including names, relationships, reference values, expected status, and other seeded constants. For example, Chipset Partner data includes the Processor partner, Chipset Partner, Chipset Series, and Chipset records.
- Import typed seed data into specs. Never duplicate seeded names, IDs, labels, relationships, or reference values as constants inside a spec.
- When a fixture requires provisioning or upload, run that setup before the dependent test or suite navigation, verify its real API response, and scope cleanup to the current E2E run. Prefer a protected setup endpoint or repository seed process over browser-created shared prerequisites.
- When a fixture requires provisioning or upload, run that setup before the dependent test or suite navigation, verify its real API response, and scope cleanup to the current E2E run. Prefer a protected setup endpoint or repository seed process over browser-created shared prerequisites. A fixture file is a data contract, not a seeder; confirm a real setup or pre-existing-data contract before adding row-dependent scenarios.
- Assert a required grid row before registering the API response waiter for opening it. Missing fixture data should fail as a clear prerequisite issue, without leaving a dangling waiter or falling back to an arbitrary live row.
- Determine each derived record's actual creation flow and cleanup path from its owning implementation; do not assume related records are provisioned together.
- Keep seed setup and cleanup helpers with the fixture or its dedicated setup module. Do not hide setup in page helpers or silently fall back to arbitrary live rows.
- If setup, approval, or cleanup is unavailable, keep runnable read-only coverage, omit dependent mutation scenarios, and report the exact gap. Do not commit skipped placeholder tests.

## Local Commands

Before running a shell command, explicitly verify or set its working directory; do not infer it from the open file or a previous terminal command. Run focused `npm` Playwright commands from `src/client`, and run `./start.sh e2e` from the repository root. If the terminal tool cannot set a working directory, change directories in the command before invoking the project script.

Run the complete suite from the repository root after Aspire is running:

```bash
./start.sh e2e
```

Use the client commands for focused diagnosis or headed execution:

```bash
npm run test:e2e -- e2e/<spec>.spec.ts
npm run test:e2e:headed
```

Set `PLAYWRIGHT_CLIENT_BASE_URL` and `PLAYWRIGHT_ADMIN_API_BASE_URL` only when testing other approved endpoints. Supply the signing key through `E2E_TEST_AUTH_KEY` or the ignored root `.env` entry `E2ETestAuthentication__Key`. Never expose the key in chat, logs, source control, or test output.

For an anonymous scenario, override storage state in the relevant describe block:

```typescript
test.use({ storageState: { cookies: [], origins: [] } });
```

Never use this workflow against shared development, staging, or production without a separately approved scope, dedicated identity, and data policy.

## Repository Learnings

- Playwright specs belong only in `src/client/e2e`; colocated specs under `src/client/src/app` are Angular unit or component tests and must remain in place. Add complementary guard E2E coverage only when a real route, deterministic identity, and browser-visible outcome exist; leave permission branch matrices covered by focused unit tests.
- When a custom web component does not expose a reliable semantic role, locate its host by component element name, such as `page.locator("md-modal-confirm")`, then scope user-facing role, label, placeholder, or text locators within that host. Do not assign an ARIA role to a component in the test that its rendered accessibility tree does not provide.
- Plain buttons that contain an icon component plus visible text can expose an accessible name containing the icon glyph, so exact role locators may time out. Scope to the owning component and locate the button structurally, filtering by visible text; do not invent an ARIA role or use a page-wide text match.
- Typeahead selections can leave a `cdk-overlay-container` list open after the valid item is clicked, causing the next button click to be intercepted by an overlay `li`. Verify the overlay is closed and use `page.keyboard.press("Escape")` when needed; never force-click the covered control or add an arbitrary wait.
- For a read-only Admin Settings list journey, assert the successful search response and stable page structure instead of requiring an environment-specific row name. Record that no baseline row is required and that an empty result remains valid.
- Admin Companies create and edit flows are two-step: **Create Company** or **Edit Company** opens a confirmation modal, then **Create** or **Update** submits `POST /Partner`. The confirmation is rendered in an `md-modal-confirm` host that does not expose the ARIA `dialog` role. The host can report hidden because it has no visible box, and inactive hosts can remain in the DOM; use it only as a scope, then filter and assert the visible descendant action, such as `page.locator("md-modal-confirm").getByRole("button", { name: "Create", exact: true }).filter({ visible: true })`. Register the `POST /Partner` response wait before clicking the confirmation action and await its successful response before asserting that the editor closed. Partner contact emails reject plus-addressing because the domain regex does not allow `+` in the local part; use accepted characters such as a dot or hyphen when generating unique E2E addresses. If the editor heading remains visible after a save, inspect the response body and any visible error notification before changing the locator or timeout. Do not treat the still-open editor as a timing issue by default: `AwaiterService.awaitAction` catches save errors and leaves it open.
- `PartnerProvider.SaveAsync` creates a primary brand named after a new company only for **OEM** and **Processor** (`PartnerTypes.Oem` and `PartnerTypes.Processor`; client `PartnerTypeId.Chipset` is ID 5). Retailer and Windows do not receive a default brand. Admin Brands company-type scenarios create one uniquely named company per type and check exactly one matching brand row for OEM/Processor or none for Retailer/Windows. Deactivate generated brands through the Brands UI, not by deactivating their companies; company records remain. Brand CRUD scenarios instead use the existing active OEM company declared in `e2e/fixtures/company.seed.json` (currently Acer in the local data set), create unique brands, and deactivate those brands. This fixture is a required pre-existing record, not a company creation script. The Company Type select uses a `listbox` with unnamed `listitem` elements whose visible child text is the type name, so locate `getByRole("listbox").getByText("OEM", { exact: true })` rather than a named listitem. The full Brands workflow has not yet passed in the browser.
- Miracle UI typeahead suggestions render under `md-options-panel` as a `ul` with `li` choices, not ARIA `option` elements. A choice can contain a primary-name span and a secondary-label span (for example, company name and partner type), so its combined text may not exactly equal the primary name. After filling the typeahead textbox, scope to the panel's `listitem` and filter by its exact primary text, such as `page.locator("md-options-panel").getByRole("listitem").filter({ has: page.getByText(companyName, { exact: true }) })`. The panel may be outside the owning modal; check the accessibility tree rather than assuming a modal-scoped list. This structure is backed by the rendered HTML and the failed Brands snapshot.
- Admin Settings `md-input` emits its debounced search change from `keyup`; Playwright `fill()` changes the visible value but does not trigger that handler. After filling a changed search value, press `End` before awaiting the search response. Compare the current input value first and skip the response wait when unchanged; a trace with only the initial search response indicates the input event did not trigger a new request.
- Grid coverage must assert the source-defined visible column labels in their rendered order. When a grid uses `rdx-dms-skeleton-grid`, hold its initial read request with `page.route`, assert that the skeleton renders the same ordered labels, then release the request and assert its successful response. For every `sortable: true` column covered, click its `Sort by <label>` header three times and assert the corresponding read requests: ascending sort key/direction, descending sort key/direction, then both sort fields removed. Encapsulate repeated area-agnostic grid assertions in `e2e/support/grid.ts`; keep area-specific helpers within their owning area. Derive the backend sort key from the owning component's sort mapping rather than guessing it.
- `openAdminGridPage` should register the initial search-response wait before navigation, use `page.goto(..., { waitUntil: "commit" })`, then await both the response and page heading. These SPA routes can render and issue their API request while the document `load` event remains pending.
- Success notifications can intercept later grid or menu clicks. Their accessibility snapshot can name the surrounding close wrapper **Close notification** while the nested button is named only **button**. Scope to each visible `.notificationContainer`, click its nested button after the animation stabilizes, and retry the intended action instead of force-clicking or sleeping.
- Each E2E global setup renews the configured user's `LoginInfo.AccessToken`; a previously issued cookie then has no matching token and can produce `NotAuthenticatedException` logs. Avoid overlapping runs or using an older session for the same dedicated identity, and inspect request timing before attributing an individual test failure to those logs.
- All supported launch paths use `scripts/run-playwright.cjs`, whose ignored lock directory rejects overlapping executions before global setup can invalidate an active run's token. `--list` skips the lock because it does not execute global setup. If a terminated process leaves the lock behind, verify that no E2E run is active before removing it.
- The Admin API fails when the current mutation-heavy E2E suite runs with parallel workers. Keep `workers: 1` in `playwright.config.ts` so spec files execute serially; do not enable parallel execution unless the API and test-data isolation have been validated for concurrent scenarios. Do not split the suite into concurrent per-file Playwright processes because each process renews the same identity.
- `global.setup.ts` sets `PLAYWRIGHT_E2E_RUN_ID` before workers start. Build generated display names with `uniqueE2EName()` and compact generated values such as email local parts with `getE2ERunId()`; retain a per-record discriminator so a retry cannot collide with a record from its earlier attempt.
- Prefer an exact named fixture for reference data. When the acceptance criterion permits any configured typeahead option and no named fixture exists, use `selectDeterministicTypeaheadOption()` from `e2e/support/admin-settings.ts`; never bind behavior to the API or DOM's first result. A visible locator can still include rendered options outside a scrollable panel's viewport, so sample only an exposed option; do not assert `toBeInViewport()` after sampling because the panel can shift between the sample and assertion. Let Playwright click perform its normal scroll/actionability checks. Keep named fixture values in the typed seed module, not in the spec.
- For every created admin record, set the cleanup state immediately after the successful save response, before editor-close and grid assertions. Clean active records in `finally`, first reopening the owning grid so failed assertions and leftover modals, drawers, menus, or notifications do not block deactivation. Reload when already on the owning route because same-route SPA navigation may not emit a fresh grid search request.
- Not every confirmation uses `md-modal-confirm`. Typed-name confirmations (for example **Deactivate Company**) open the DMS `DeleteConfirmModalComponent` through `ModalService`, rendered under the `rdx-dms-delete-confirm-modal` host. Its Miracle input updates through `textChange`; after `fill()`, press `End` and wait for the action button to become enabled. Before scoping a modal, check which component the page passes to `modalService.open(...)` and use that component's selector.
- Multi-step Admin Settings mutation suites can validly approach Playwright's default 30-second test timeout. Use a bounded suite timeout that includes `beforeEach` and cleanup, while leaving focused locator and API waits unchanged so a stalled operation remains diagnosable.
- Admin panel **More Actions** dropdown items (built from `getMoreOptions()` `Section` entries with an `icon`) render as `<button class="container">` inside `rdx-dms-dropdown-panel-item`, with an icon-font glyph before the `.title` span, so exact name matches fail. The **More Actions** wrapper (`.admin-panel-action-list__dropdown-wrapper`) is itself a button containing every item, so page-wide suffix regexes such as `/Edit Company$/` hit strict-mode violations, and `/Activate Company$/` also risks matching **Deactivate Company**. Scope to the item host and match the title exactly: `page.locator("rdx-dms-dropdown-panel-item").getByRole("button").filter({ has: page.getByText("Edit Company", { exact: true }) })`. Direct action-list buttons (for example **Deactivate Company**) do match exactly.
- Miracle UI grid cells are not the interaction owner. Plain-text cells render under a `.tooltip` wrapper whose `.tooltiptext` sibling can cover the cell and intercept Playwright pointer actions after hover. Locate the identifying `gridcell`, move through its `.tooltip` parent to the `.grid-body-item.clickable` row ancestor, assert that ancestor is clickable, and click the row instead of forcing a cell click.
- Scope nested menu locators to their named navigation, such as `getByRole("navigation", { name: "Targeting" })`. Menu items include icon-font glyphs in their accessible names, so use a stable suffix match such as `{ name: /Language$/ }` when an exact text name does not match the accessibility snapshot.
- Contributor Collections is a Windows-brand route at `/dms/collections`. The board loads with `POST /CollectionVersion/search`; list filtering can use a guaranteed nonmatching query and assert **No collections found** without baseline data. Opening the editor is read-only but requires at least one existing collection: select an `Open collection ...` button, assert `GET /CollectionVersion/get-by-id`, the `collection-id` query parameter, selected `aria-pressed` state, and close-button restoration to the list-only URL. Treat a missing row as a test-data failure rather than weakening the editor assertion.
- Use `test-results/**/error-context.md`, the failure screenshot, and the trace to distinguish a locator defect from a product, data, authentication, or environment failure before changing code.
- Admin Settings pages share one structure; follow `.github/instructions/dms-e2e-admin-tests.instructions.md` and reuse `e2e/support/admin-settings.ts`. Roles & Access (`e2e/admin-settings/roles-and-access.spec.ts`) requires only a role name and description to enable **Create Role**; the company type, permissions, and access controls are optional in the client. Permission checkboxes are named by `md-label for`; the access-control grid checkboxes are unnamed and render View, Edit, Approve per editor type, with View checked and disabled while Edit or Approve is checked. Save is `POST /Role`, deactivation `DELETE /Role/set-inactive`, activation `PUT /Role/set-active`. This spec has not yet passed in the browser.
- Members (`e2e/admin-settings/members.spec.ts`) uses `/admin-settings/members` and requires Company, Role, and Brand selections for member creation. Before running mutation scenarios, obtain approval for the dedicated system-admin identity, reference-data contract, mutations, and cleanup; do not use an existing member as a test fixture without approval. The page uses `POST /User/search`, `POST /User`, `GET /User/get-by-id`, `DELETE /User/set-inactive`, `PUT /User/set-active`, `POST /User/set-system-admin`, and `POST /User/resend-invite-mail`. The spec includes independent search, add/edit, deactivate, and reactivation scenarios with newly created members; an invited member returns to **Invited** after activation until first login. Resend-invite and system-admin toggle scenarios still need approved identities and mutation scope.
- Miracle `md-input-text-area` (dynamic-form `textarea` fields such as **Description**) pushes its value to the form control only from a 250 ms debounced `keyup` handler. `locator.fill()` fires `input` but not `keyup`, so the textarea shows text while the form still reports "Description is required." and the submit stays disabled. Use `fillTextArea` from `e2e/support/admin-settings.ts` (fill, then press `End`). The first Roles & Access run failed this way on create, required-field, and lifecycle scenarios.
- Admin grid Status badges (`md-badge` with the `activeDisabled` pipe) render two `<span title="Active">Active</span>` elements in the DOM while the accessibility tree shows one `gridcell "Active"`. `row.getByText("Active", { exact: true })` therefore fails in strict mode; use `getStatusCell(row, "Active" | "Inactive")` from `e2e/support/admin-settings.ts`. Observed in the Roles & Access reactivation scenario.
- Keep deactivate and reactivate as separate tests. Reactivation arranges an inactive record through a `createInactive<Entity>` helper, asserts only the activation outcome, and deactivates in `finally` only after a successful activation.
- The validated system-admin example is `src/client/e2e/admin-settings/targeting-parameters/navigation.spec.ts`: Home user menu to **Admin Panel**, **Targeting Parameters**, default **Device Config List**, then **Language**, with HTTP `200` from `POST /Language/search` and no targeting-data mutation.
- Admin Targeting Form Factor at `/admin-settings/targeting-parameters/form-factor` has no filters or reference-data requirements. Its Add drawer (`rdx-dms-form-factor-drawer`) contains only the required `Enter a Form Factor Name` field (maximum 200 characters), with no aliases; the grid shows Status only on **All**. `form-factor.spec.ts` includes Add/Edit/Deactivate/Activate with run-unique cleanup; browser execution remains unverified.
- Admin Targeting Content Type at `/admin-settings/targeting-parameters/content-type` has no filters or reference-data requirements. Its Add drawer (`rdx-dms-content-type-drawer`) requires `Enter a Content Type Name` (maximum 250 characters) and `Enter the Download Priority` (0–9), with no aliases. `content-type.spec.ts` includes Add/Edit/Deactivate/Activate; scenarios are authored but not browser-verified.
- Admin Targeting Language at `/admin-settings/targeting-parameters/language` has no filters or reference-data requirements. Its Add drawer (`rdx-dms-language-drawer`) requires Name and a unique Locale Code; BCP 47 is descriptive only and is not validated by the form. `language.spec.ts` includes Add/Edit/Deactivate/Activate; scenarios are authored but not browser-verified.
- Admin Targeting OEM, OEM Series, and Retailer are derived models with disabled Add actions. Their specs (`oem.spec.ts`, `oem-serie.spec.ts`, and `retailer.spec.ts`) intentionally cover only row-independent grid behavior; drawer and lifecycle coverage need a real provisioning or verified pre-existing-row contract and explicit mutation approval.
- Admin Targeting Platform, Region, Resolution, and OS Edition have no reference-data prerequisites and now include Add/Edit/Deactivate/Activate scenarios with cleanup. Region's two-letter code guidance and Resolution's display notation are tooltips, not validators; Region codes are unique per run.
- Admin Targeting OEM Model requires configured OEM and OEM Series options; OS Version requires a configured Platform. Their specs include Add/Edit/Deactivate/Activate and select options deterministically. OS Version's Minimum/Maximum Version fields validate dotted numeric strings (`^\d+(\.\d+)*$`, maximum 32 characters).
- OS Version's drawer allows shorter dotted versions, but `POST /OSVersion` rejects `1.0` and `2.0` with invalid Minimum/Maximum Version messages; use three-segment values such as `1.0.0` and `2.0.0` in mutation scenarios. Its grid filter placeholder is **Select a Platform**, distinct from the drawer's **Select Platform**.
- Content Type initializes Download Priority to `0`; `md-input-number` clamps `10` to `9` after keyboard interaction instead of leaving Save disabled. Assert the normalized field value and Save state when testing the 0-9 range.
- Admin Targeting Retail Access Code requires Name, Display Name, Retailer, and a Brand dependent on Retailer; Admin Password is optional. Store ID's API root is `/Store` (not `/StoreId`); its Add drawer requires Store ID, Store Name, and Retailer, while Address, Region, and Is MISX are optional. Both specs include lifecycle scenarios and need configured retailer options; Retail Access Code also needs an associated Brand.
- Admin Targeting SKU requires Name and Retailer. OEM, Locale, Form Factor, Resolution, Screen Size, and Notes are optional; OEM Model appears only after an OEM is selected. Its grid filters include OEM, OEM Model, Retailer, Locale, Form Factor, and Resolution. The spec includes lifecycle scenarios and needs a configured Retailer.
- Admin Targeting Collections requires a Windows Company and associated Brand plus a completed targeting set. Its spec creates a Region target and edits by adding Platform because Collection Name is locked after creation. Lifecycle scenarios clean up by deactivation and require configured Windows Company/Brand, Region, and Platform options. A successful `POST /Brand/search` with `results: []` after selecting a Windows Company is a missing Company/Brand reference-data contract; require a verified pair instead of choosing another arbitrary live company.
- Admin Targeting GPU and NPU use `POST /Gpu/search` and `POST /Npu/search`; both pages have a Chipset Partner filter and Add drawers requiring Name plus Chipset Partner, with aliases. Their specs cover Add/Edit/Deactivate/Activate with run-unique cleanup; activation is a separate scenario. A configured Chipset Partner is required; hard delete is unsupported.
- Inventory every Admin Settings page's panel actions, conditional More Actions, confirmations, and detail surfaces before writing tests. Give each supported action an independent scenario; explicitly report missing fixtures or approval rather than dropping actions. Admin Integrations (`e2e/admin-settings/integrations.spec.ts`) is system-admin-only at `/admin-settings/integrations`; its activation scenario is browser-verified, while the complete action spec still requires a full run before claiming broader verification. Its editor host is `rdx-dms-edit-company-modal` despite its heading. Name, Data Type, and retailer Company are required; choosing fixed **Store** avoids conditional Brands. Create/edit confirm before `POST /Integration/save`, and a successful save must be marked for cleanup immediately. Panel **Delete** deactivates through `DELETE /Integration/set-inactive`; an inactive integration activates through `PUT /Integration/set-active`. Unlike other Admin Settings pages, **Open Details** opens `rdx-dms-panel-integrations`, which loads `GET /Integration/get-by-id` and offers separate activation/deactivation actions. Secret regeneration is a further mutation and must never expose the secret. Parser Settings appears only for SKU-list integrations. Require an existing retailer and explicit authorization for each run's auth renewal, integration mutations, and cleanup. See `.github/instructions/dms-e2e-admin-tests.instructions.md` for the detailed checklist.
- Admin Members, Roles & Access, Companies, Brands, Integrations, and Workflows share search/add/edit/deactivate/activate actions; a cleanup deactivation in an add test is not independent deactivation coverage. New activation scenarios in Brands and Companies arrange inactive unique records, then deactivate them again. Members invited by the add flow return to **Invited** after activation until first login; resend-invite and system-admin changes need dedicated approved identities. Workflows require an unused content-type/company/brand specificity and a valid approver role, so do not create against an arbitrary existing combination. Ticketing is different: it hides Delete and More Actions, and opens an inline panel on row selection; do not invent activate/deactivate. The current Workflow and Ticketing specs are read-only starter coverage; mutation and baseline-row scenarios still need deterministic fixtures and approval. See the Admin Settings instructions for the page-by-page gaps.
- Profile Settings currently renders only the `profile-settings works!` placeholder from `ProfileSettingsComponent` and makes no API request. Keep the smoke test focused on the route and visible component until the page implements API-backed behavior; do not expect `GET /User/authenticated-user` from this placeholder.

## Completion Gate

- Every assertion maps to an acceptance criterion.
- The test is independent and repeatable with documented seeded data requirements, including an explicit no-seed contract when applicable.
- No secret or generated browser artifact is tracked.
- Suite execution and any scenario-specific data mutation were explicitly approved.
- Focused execution evidence is reported without claiming checks that were not run.
